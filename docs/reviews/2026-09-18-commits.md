## Reproducible findings

### R1 — P1: unreadable files are mistaken for deleted files, enabling loss of foreign bytes

**Locations:** `packages/workspace/src/write.ts:212–234,279–303`;
`packages/workspace/src/session.ts:730–737`.

`readFile` catches every error and treats it as absence. For an established
project, write foreign bytes to `scenes/main.json`, then `chmod 000` that file
(directory remains writable). A mutation reports `external_change_unresolved`
but snapshots **zero bytes**, with the SHA-256 of empty content. A subsequent
`discardExternalState` succeeds: `allowAbsent` accepts the same EACCES read and
rename destroys the unreadable foreign file. This was reproduced with real
permissions as the unprivileged host user, not a mock. No snapshot of the actual
foreign content exists.

**Repair/acceptance:** distinguish ENOENT from EACCES/EIO and other failures in
pre-checks and final classification. Fail closed on unknown content; never
manufacture a deletion snapshot or allow replacement from an unreadable read.
Add permission-denied and transient-read-error tests, including discard. If a
new unknown-disk-state error is necessary, review the contract diff explicitly
rather than falsely reporting `previous`/`new-undurable`.

### R2 — P1: a write retry overwrites foreign content without another pre-write check

**Location:** `packages/workspace/src/write.ts:212–239,256–275`.

The hash check is outside the retry loop. Inject a first-attempt rename failure
that leaves foreign bytes at the target. The second attempt overwrites those
bytes and returns success; no recovery snapshot exists. This is not merely the
contract's unavoidable check-to-rename race: an entire new W attempt begins
without checking the current target. Workspace §5.2/§7.1 require an immediately
preceding hash check before overwriting unknown content.

**Repair/acceptance:** re-check before every attempt, track whether this W already
installed its own intended bytes, and permit that known intermediate state when
retrying a failed directory flush. A newly foreign target must be preserved,
snapshotted and paused, not overwritten. Test both failure-before-rename and
failure-after-rename with an intervening foreign write.

### R3 — P1: failed recovery snapshots are ignored; discard can destroy the only evidence

**Locations:** `packages/workspace/src/session.ts:591–593`;
`packages/workspace/src/recovery.ts:48–60,91–100`.

`detectExternalChange` ignores `snapshotForeignBytes` returning null. Inject
ENOSPC on recovery-file creation, leave foreign envelope bytes, and trigger a
mutation. The only result is ordinary `external_change_unresolved`. Discard then
returns success and overwrites the foreign bytes despite **zero recovery
snapshots**. The recovery helper's comment claims the caller reports snapshot
failure; it does not. This violates workspace §5.5 G1.3 and §7.2–§7.4.

**Repair/acceptance:** explicitly track/report failure to preserve evidence;
retain a fail-closed pause and prevent destructive resolution until the exact
foreign bytes have been durably snapshotted (including retrying snapshot
creation after disk recovery). Document the failure-state/error semantics via a
reviewed contract addendum. Test recovery-directory ENOSPC/EACCES/fsync failure
followed by both accept and discard.

### R4 — P1: failed ownership release leaves the old backend writable after another claims it

**Locations:** `packages/workspace/src/session.ts:1034–1050`;
`packages/workspace/src/ownership.ts:375–387`.

Fault directory fsync only for `.thirdlight` during release. The released
ownership record reaches disk, but release returns
`write_failed {onDiskState:"new-undurable"}` **before** setting the session mode
to released. A second service identity can claim the released record and load
revision 0. The first service still accepts a mutation and advances to revision
1, while the new owner continues serving revision 0. No simultaneous-claim race
is required: this is a sequential, reproducible split-brain.

**Repair/acceptance:** once the ownership record is released on disk—or foreign
ownership is observed—the old session must not remain an active writer. Handle
all ownership-write outcomes explicitly while still returning failure for
unproven durability. Add a two-identity regression covering release fsync
failure, second claim, and attempted old-owner mutation/release; the old backend
must not act on cached ownership.

### R5 — P1: operator envelope writes ignore `new-undurable`, leaving memory inconsistent with disk

**Locations:** `packages/workspace/src/session.ts:702–714,1020–1029`
(and audit the equivalent discard branch at `746–752`).

Unlike `runCommand`, accept/release immediately return on **every** `res.failed`
without publishing the intended state when rename already took effect.
Reproduced with scene-directory fsync faults:

- Accept external revision 10 from LKG revision 1: return `new-undurable`, disk
  revision **10** with retry records cleared, queries still serve revision **1**.
- Release after a successful mutation: return `new-undurable`, disk retry list
  is **empty**, yet retrying the original request returns `duplicated:true` from
  the stale in-memory map. A following write treats the backend's own rewritten
  envelope as a new foreign edit because `lastWrittenHash` is stale.

Workspace §5.1/§5.2 require the intended state/hash to become the running state
on `new-undurable`, while the operation still returns failure.

**Repair/acceptance:** reconcile scene/revision/records/hash/history/pending
state at every operator write boundary, not only ordinary mutations. Define the
operator boundary behavior explicitly where needed; fault-test each stage of
accept/discard/release and compare disk, queries, dedup, subsequent commands,
and restart behavior.

### R6 — P2: temp-file close errors are swallowed and success is acknowledged

**Location:** `packages/workspace/src/write.ts:248–254`.

The catch comment says close failure is an I/O error, but the exception is
swallowed and rename/fsync/verification continue. Inject EIO from `closeFile`
(after actually closing the descriptor): a mutation returns `ok:true`, revision
1. Workspace §5.1 requires sequence I/O failures to enter bounded retry and
classification, not success.

**Repair/acceptance:** propagate the close failure through W's failure handling
without masking an earlier write/fsync failure or retrying a potentially reused
fd. Add a close-only fault test that never returns success when all attempts
fail at close.

### R7 — P1: containment checks are bypassed by startup scan and child-directory symlinks

**Locations:** `packages/workspace/src/service.ts:538–593,647–662`;
`packages/workspace/src/session.ts:180–192`; envelope writes use `scenes`
without checking its resolved path.

Two real-filesystem repros: (1) put a project-directory symlink under the root,
pointing at an outside directory containing only a valid manifest and `scenes/`;
opening the service **creates `main.json` outside the root**, although a query
subsequently rejects that project; (2) point an open project's `scenes/` at an
outside directory containing its envelope; a normal mutation successfully
writes there. Checking only the project directory at on-demand open does not
satisfy packet 07's symlink-escape requirement.

**Repair/acceptance:** apply one documented containment/symlink policy to scan,
creation, reads and every write/artifact path, including `scenes`, `.thirdlight`
and recovery; reject escapes before any modification. Test both repros plus
nested artifact symlinks, not only a top-level query escape. Define separately
any unsupported hostile path-replacement race; do not claim this is solved by
checking only the outer directory.

### R8 — P1: ownership/liveness I/O errors are treated as absence/death

**Locations:** `packages/workspace/src/ownership.ts:111–119,143–146,187–193,210`.

With an active owner, chmod its ownership file to 000. A second identity's query
successfully **overwrites the live claim** because unreadable bytes become
null and null means absent. Separately, use the supported procRoot seam with
an inaccessible `<procRoot>/<pid>/` directory: stat EACCES becomes “dead,” query
reports `stale_ownership`, and explicit takeover succeeds while the real owner
is alive. These contradict §6.2's conservative unknown⇒live rule.

**Repair/acceptance:** preserve missing/unreadable distinctions through the
ownership API and filesystem existence checks; only proven absence/death permits
a claim/takeover. Test real ownership-file EACCES and proc stat/read errors;
assert original record unchanged and both automatic claim and takeover denied.

### R9 — P1, CONTRACT BLOCKER: rename plus verification does not establish exclusive ownership

**Locations:** `packages/workspace/src/ownership.ts:287–315`;
`docs/contracts/workspace.md §6.3–§6.4`.

Deterministic interleaving via the public WriteOps seam: A evaluates the record
as absent and pauses immediately before its ownership rename; B claims and
verifies successfully; A resumes, overwrites B and verifies successfully. **Both
opens succeed and both sessions remain open.** This models a permitted
multi-process interleaving without requiring a probabilistic race. The earlier
review explicitly did not exercise it. Envelope prechecks cannot establish
ownership while both sessions have loaded the same envelope hash.

The implementation follows the accepted contract's flawed claim primitive, so
**do not silently repair this by changing ownership semantics**. Request an
architectural contract revision: a truly exclusive claim/lifetime mechanism
(and corresponding crash/takeover/release semantics), replacing the false
“concurrent claimers converge to exactly one winner” assertion. A second reread
or another finite hash check does not make rename a compare-and-swap.

**Acceptance:** reviewed contract diff and deterministic interleaving tests,
then real two-process barriers demonstrating exactly one active writer for
absent/released/stale claims. Reopen the relevant architectural gate before
implementing the revised primitive. Real two-process race testing was not run
by this audit; the sequentially scheduled interleaving was reproduced.

### R10 — P1: public query/ack objects expose mutable authoritative state

**Locations:** `packages/workspace/src/session.ts:1264,1300,1316–1325`;
`packages/workspace/src/service.ts:169,193,229`.

Change `queryEntity(...).entity.name`: later queries show the change at the same
revision, and an unrelated command persists it. Separately, change a returned
success's `history.undoDepth` to -1: a retry returns that corrupted value, and
the next command persists a retry record rejected at reopen. Replays shallow-copy
only the top level. These are ordinary in-process consumers of the public API;
no filesystem bypass or unsafe cast is required in JavaScript.

**Repair/acceptance:** deep-isolate or immutably protect every exported value
(query entities/subtrees, manifest, fresh/replayed acknowledgements, nested
errors). Test caller mutation of each result followed by queries, retry,
unrelated mutation and reopen. Only `runCommand` may mutate authoritative
state; TypeScript readonly declarations alone are insufficient.

### R11 — P1: an optional undefined property makes a successful command poison its own envelope

**Locations:** `packages/workspace/src/service.ts:162,189–193`;
`packages/workspace/src/digest.ts:54–60`.

An otherwise valid create request with `origin: undefined` succeeds. Digest
canonicalization returns null, but `D!` merely suppresses the type warning; disk
gets `"digest": null`. Identical retry reports `request_id_reused`, and reopen
fails `retry_records_invalid`. This affects direct JS callers constructing
optional properties, not literal JSON wire requests.

**Repair/acceptance:** reject noncanonicalizable fresh inputs before building any
record (or explicitly define safe normalization without changing canonical wire
semantics). Preserve dedup/pause/revision ordering. Test undefined optional
fields and other non-JSON values; no successful command may produce an envelope
its own loader rejects.

### R12 — P1: malformed persisted JSON can abort the entire service startup

### R15 — P2: idempotent `createProject` incorrectly opens/claims existing projects

**Location:** `packages/workspace/src/service.ts:366–368`.

The existing-directory path calls `ensureSession` instead of checking loadable
disk state without side effects. Reproduced: a healthy project owned by another

**Repair/acceptance:** separate read-only existence/load validation from
session/ownership acquisition. Test valid-owned, valid-released, cached-but-now-

### R16 — P2: same-second pruning can delete the snapshot just created

**Location:** `packages/workspace/src/recovery.ts:107–118`.

Pruning sorts `timestamp-hash` filenames, so within one second it keeps snapshots
by **hash**, not age. Generate 17 distinct foreign values with a fixed valid
stamp, arranging descending hash order. The 17th snapshot is immediately
pruned, and discard succeeds with its foreign evidence no longer retained.
§7.2/§7.4 promise the oldest snapshots are pruned, retaining the current evidence.

**Repair/acceptance:** track reliable creation ordering for tied timestamps and
always retain the just-created snapshot. Review any artifact naming/schema
change first. Add >16 same-second detection/resolution cycles and verify the
newest 16, including the currently pending change, survive.

### R17 — P2: query validation errors may not be JSON-serializable

**Location:** `packages/workspace/src/errors.ts:288,325`.

Public `query(unknown)` accepts arbitrary inputs for validation, but a BigInt
`op`/`args.limit`, or cyclic `args.entityId`, is copied into `error.found`.
`JSON.stringify(result)` then throws. These are in-process API cases, not valid
JSON wire inputs; nonetheless the validator must not manufacture an unserializable
protocol error.

**Repair/acceptance:** use bounded, JSON-safe diagnostic conversion for all
`found` fields (depth/node/string limits, cycles and unsupported primitive types).
Test that malformed public input always yields a serializable bounded failure.
