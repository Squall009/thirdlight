# Phase 29 — Scalable lighting

Goal: a lit 3D scene with dense foliage and several flickering local lights
holds 60 fps at 1080p on an integrated GPU. Indirect light comes from probes
baked from the scene's static objects and lights every 3D object; static
shadows are rendered once and cached; only moving objects cast shadows each
frame. The design follows Unity HDRP, Unity's probe volumes and Unreal (§3).
Read `docs/roadmap.md` (principles 1, 1b and 7) first. Phase 29 starts after
phase 28b (immediate block and texture fixes, after phase 28's second batch of game requests). Requests: Skyforge Tactics E45 and E43 (effect lights;
`~/projects/skyforge-tactics/docs/engine-gaps.md`), and the owner.

## 1. Owner decisions (2026-09-29)

- **Tiers 1 and 2 of the lighting review are this phase; tier 3 is written
  down (§5) and done only if the measurements demand it.**
- **The lighting model:**
  - Objects marked `static` are what the bake sees: they bake the indirect
    light into probes and the static shadows into cached shadow maps.
  - **Probes light every 3D object** with indirect light, placed
    automatically over the scene. Lightmaps stay optional, for surfaces that
    want baked detail.
  - **Static objects** get direct light, the cached static shadows, and the
    shadows moving objects cast.
  - **Dynamic objects** (characters, anything that moves) get direct light,
    indirect light from the probes, and the static shadows. Only they cast
    shadows every frame, into a separate dynamic map combined with the static
    one where they are.
- **Target:** 60 fps at 1080p on this host's Intel Iris Xe, measured
  uncapped. 30 fps is not acceptable for timed input. The owner's laptop (an
  AMD Ryzen 4000-series APU, Radeon Vega graphics) is the low end: getting
  near 1080p 60 fps there, dynamic resolution included, counts as a win.
  Its Chrome reports WebGPU hardware accelerated (owner, 2026-09-29).
- **Foliage is real geometry** (no alpha cutouts), so the cost is vertices
  and many small triangles, not overdraw from alpha testing.

## 2. Where things stand (checked at `ccc682b`, 2026-09-29)

- **Local lights** are three `PointLight`/`SpotLight`s
  (`three-adapter/src/adapter.ts:573-597`). three evaluates every visible light
  per pixel on every lit material, grass instances included. No culling.
  Budget: 16 per view (`scene-v3.ts:165`, `scene-lights.ts:23`, over-budget
  lights switched off), plus a separate pool of 16 effect lights
  (`effects-draw.ts:627`).
- **Light modes** `realtime | baked | mixed` exist (`scene-v3.ts:304`). A
  baked light's contribution is summed into one lightmap atlas; the only
  runtime change is a tint over the whole map (`lightmaps.ts:85-95`).
- **Lightmaps** (phase 9.6): browser baker (direct only) and Blender Cycles
  (bounces). Bake targets are static `box`/`model` entities only
  (`editor/src/viewport/bake-run.ts:110`); instance sets and block layers are
  skipped (block-layer lightmaps are 25.20).
- **Shadows:** one directional map, no cascades, around the camera's start
  square (`three-adapter/src/lighting.ts:136-245`); point 512 cube, spot
  1024. Every shadow map is re-rendered every frame with every caster
  (no `autoUpdate`/`needsUpdate` use); instance sets always cast.
- **No light probes, no ambient occlusion, no render scale, no light
  layers.** A material can already be given a subset of lights internally
  (`withoutAmbientLight`, `node-materials.ts:96-115`).
- **Effects:** a system with a light output moves the whole effect to the CPU
  executor (`effects-gpu.ts:63`).
- **Two realizations:** the editor's Scene view builds lights, materials and
  lightmaps itself (`editor/src/viewport/viewport.ts:469`, `:1417`) next to
  the adapter's (`adapter.ts:805`, `:1371`); defect D27 was the two drifting.
  `adapter.ts`'s `createSceneAdapter` is one 1,700-line closure.
- **Perf harness** (`tools/perf`): classes up to 16 point lights, no foliage
  or block-layer class, 1280×720 default, frame time from
  `requestAnimationFrame` (vsync-capped), no GPU pass timings.
- **Skyforge's numbers** (E45; small headless canvas, likely capped, so they
  understate 1080p): 7–8 flickering point lights over ~4,000 grass instances
  drop Play from ~58 to 38–42 fps on this host's iGPU; draw calls, shadows
  (off) and the wind shader were ruled out.

## 3. How other engines do it (checked 2026-09-29)

| Topic | Unity | Godot 4 | Unreal | Thirdlight after phase 29 |
|---|---|---|---|---|
| Cached shadows | HDRP Update Mode Every Frame / On Enable / On Demand; "Always draw dynamic": static casters cached, dynamic casters each frame (a blit from the cached map, both atlases in memory) [1] | Omni/spot shadow atlas cached until something changes; directional shadows are not cached [5] | Virtual Shadow Maps: separate static and dynamic page caches, only pages a moving caster overlaps re-render; moving the light invalidates all [6] | Static map cached per light, dynamic map each frame with only moving casters, combined in the shader (29.4) |
| Probes | Adaptive Probe Volumes: placed by geometry density, sampled per pixel; leak tools Virtual Offset, Dilation, Adjustment Volumes, rendering layers [2] | LightmapGI generates probes for dynamic objects (indirect only) [5] | Volumetric lightmap | Probe grid placed over the static bounds, sampled per pixel by every 3D object; validity, offset and dilation against leaks (29.5) |
| Static vs dynamic lighting | Mixed modes Baked Indirect, Shadowmask, Distance Shadowmask, Subtractive [3] | Light bake mode Static (direct + indirect baked) / Dynamic (indirect only) [5] | Stationary lights: static shadows baked, movable objects cast dynamic ones [6] | `mixed` lights: indirect in probes, direct realtime; `baked` lights: all in probes/lightmaps (29.5) |
| Which lights hit what | Rendering layers; built-in pipeline light Culling Mask [4] | `light_cull_mask` against VisualInstance3D layers; `shadow_caster_mask` [5] | Lighting channels | Light layers and a shadow caster mask (29.3) |
| Cheap lights | Built-in "Not Important" lights: vertex/object light mode [4] | Mobile renderer: 8 omni + 8 spot per mesh [5] | — | Per-vertex local lights per object or material (29.6) |
| Many lights | URP Forward+ | Forward+ clustered, 512 elements per view [5] | Clustered deferred | Tier 3 (§5): three's `ClusteredLighting` is WebGPU-only and skips shadowed and spot lights |

three.js r186 (pinned) provides: `LightProbeGrid` (+ `LightProbeGridWebGL`;
GPU bake to L2 SH in a 3D texture atlas, `bake()` needs WebGPURenderer; no
leak handling beyond a half-spacing normal offset, no bake layer filter)
[7]; shadow `autoUpdate`/`needsUpdate` and `shadow.camera.layers` filtering;
`light.shadow.shadowNode` replacement, with `CSMShadowNode` and
`TileShadowNode` as patterns for a node combining several shadow maps (no API
to draw into an existing map; depth copies are not portable on WebGPU) [8];
`SSAONode` and `GTAONode` (fragment passes, both backends expected) [9];
`PassNode.setResolutionScale`, `FSR1Node`, `TAAUNode` [11]. No per-vertex
lighting exists in node materials [10].

## 5. Tier 3 — only if the measurements demand it

- **Clustered lighting** (three's `ClusteredLighting`, URP Forward+, Godot
  Forward+): each surface pays only for nearby lights, and the per-view cap of
  16 local lights becomes per cluster. WebGPU only and shadowless point
  lights only in r186; WebGL 2 would need per-chunk light lists.
- **Shadows for large worlds:** cascades that follow the camera with cached
  cascades, or Unreal-style page caching (only the tiles a moving caster
  touches re-render). Phase 29 caches a fixed-extent map, which suits bounded
  levels.
- **Flickering baked light** (Quake/Source "light styles"): each switchable
  light's baked contribution stored separately and scaled at run time. Not in
  Unity or Godot; phase 29's `mixed` lights flicker their direct light and
  keep a steady baked bounce.
- **Adaptive probe placement** (APV bricks by geometry density) instead of
  grids, and probe baking in Cycles.

## 7. Decision log

- 2026-10-06 (light layers, default chosen, owner to confirm): 8 layers (the plan's number; masks are tested as 32-bit integers, so up to 31 would need no format change); absent masks mean every layer, an object is in at least one layer (`lightLayers` 1–255), a light's masks may be 0. Layers are names in `content.lightLayers` (labels only, duplicates allowed). Objects created through `createEntity` set `lightLayers` with a following `setComponent` (as `castShadow`). Effect lights ignore layers until 29.7.
- 2026-10-06 (light layers, implementation): filtering per object on the CPU (a per-object uniform on layered lights' colour) instead of material variants per mask: no program variants, no material copies (they would fight looks, lightmaps and swaps over `mesh.material`), and a mask change while the game runs builds nothing. Only a light turning plain ↔ layered is realized again (one rebuild of lit programs, like adding a light), so default masks cost nothing.
- 2026-10-06 (probe grids, default chosen, owner to confirm): spacing 2 m horizontally; a ground band 2 spacings high (from the bottom of the static bounds or volume) at half the vertical spacing, the rest at the spacing; the auto box reaches half a spacing above the static objects; tiles of ≤ 64 intervals a side (one 3D texture and one file each, neighbours share their faces); 2 bounces; a probe seeing back faces in > 25 % of its directions is invalid, tried at ¼ and ½ a spacing away from them, else filled from its 26 neighbours; 16 px cube faces, 256 SH directions. Probe volumes are axis-aligned world boxes (an entity's rotation is ignored).
- 2026-10-06 (probe grids, storage): the probes ride in the scene's bake record (`lighting[sceneId].probes`, additive optional; a record may then have no atlases), so setLighting, undo, the closure, the play manifest, export and the verified reader carry them as they carry lightmaps — no schema bump, no new asset kind. Each tile's file is a texture asset holding a 16-bit RGBA PNG of half floats (lossless: 8 bits cannot hold sunlit and dark probes), never decoded as an image (scene preparation leaves it out; the adapter reads its bytes through `lighting.loadBytes`). Light probes are not three's `LightProbeGrid.bake`: it has no readback, no validity and no way to keep non-static objects out; its atlas layout and light node are used as they are.
- 2026-10-06 (probe grids, bake): its own scene of the static meshes (small ones merged per material and 16 m cell: village 160 → 110 s; merging across the level doubled the block ground's time), the baked/mixed directional/point/spot lights with shadows drawn once, and what a probe sees of the sky as the background: the environment map (or the sky colour) plus baked/mixed ambient and hemisphere lights as radiance (I/π). Surfaces are not lit by the sky directly — through closed walls it would leak — they get it in the bounce passes, which light them with the previous pass's probes. A light's own direct light is not in the probes (no emitter is drawn): `mixed` lights hold their bounce only, as planned; `baked` lights' direct light for dynamic objects is part B's call (probes with an SH term per baked light, or keep them realtime for dynamic objects). Light layers are not applied in the bake; instance sets are not in it (as for lightmaps).
- Part B notes: `createProbeGridSet` (three-adapter `probe-grids.ts`, held as `probeGrids` in adapter.ts, following the realized scenes) gives `tiles()` → `{ sceneId, grid, light }` with `light` a three `LightProbeGrid` over the tile (`texture` = the half-float atlas, `falloff` 1e-3), not in the three.js scene; `renderer.library.addLight(LightProbeGridNode, LightProbeGrid)` registers its node (probe-bake.ts does it for the bounce passes). As a light it adds to the irradiance on top of ambient/hemisphere/IBL: sampling must replace those inside the tiles, skip lightmapped copies, and pick one tile where they share a face. Each probe's validity (1 valid, 0.5 moved, 0 filled) is the alpha of its last texel (`decodeProbeArtifact`), for the debug view. Bake: `bakeProbeGrids` (probe-bake.ts), editor `probe-bake-run.ts` / `probe-bake-inputs.ts`; artifact format `probe-artifact.ts`; record and placement `project-model/probe-grids.ts`; e2e `tests/e2e/lightmaps.e2e.ts` (`bakeProbes`); measure with `node tools/perf/run.mjs probe-bake --class village|blocks`.
- 2026-10-06 (probe sampling, default chosen, owner to confirm): inside a tile the probes replace the sky's image-based diffuse light and the `baked`/`mixed` ambient and hemisphere lights (what the bake holds); `realtime` ambient/hemisphere lights stay additive (an environment preset changing them still shows; one changing a baked/mixed ambient does not reach probe-lit areas, as for lightmaps without their tint — a probe tint is a follow-up if games need it). Reflections (IBL specular) are scaled by min(1, probe ÷ replaced luminance). Outside every tile the flat ambient light stays, with a fade of one horizontal spacing past a tile's edge. Light layers: the probes light every layer. Baked lights for dynamic objects: kept as before — a `baked` light a lightmap holds is off at run time, so moving objects get only its bounce from the probes (Unity puts baked direct light into probes for dynamic objects; adding it means an SH term per baked light in the bake, with its shadow from the probe — a follow-up if wanted); `mixed` lights stay realtime direct with their bounce in the probes.
- 2026-10-06 (probe sampling, implementation): one `ProbeLighting` light per adapter (present while any bake has probes, so tiles arriving build no program) with its own light node, ordered last by a `LightsNode` subclass the renderer factory installs (three's light nodes only add; the replacement needs the ambient/IBL terms in first) — every lit material gets it without per-material hooks; lightmapped copies leave it out (`withoutProbeLighting`). All loaded tiles are packed into one 3D texture (three's atlas layout per tile, tiles side by side; 2048-texel edge, tiles past it reported as `unplaced`, no count cap) with a table; each object's likely tile comes from the CPU as per-object uniforms, the table loop runs only for pixels outside it (the per-pixel loop cost 0.33 ms). Where tiles share a face the first tile in the table (scene id, then record order) wins: both hold the same probes there, so no blend. First-order SH at run time (four samples; Unity APV's default) from the L2 files; validity-weighted interpolation (premultiplied: valid 1, moved ½, filled 1/64).

Per copy keeps the chunks and one draw per mesh and level that holds copies (a draw with none leaves three's walks); picks are made once per view and chunk (all its draws share them), only when the view, the chunk's place or the tuning changed, and a chunk wholly nearer than its first switch and its falloff or wholly past its cull is decided without a loop. Diagnostics: `renderer.lod` {bias, hysteresis, switches, copySwitches, instances {copies, inView, byLevel, culled, thinned}}; the perf harness prints copies drawn and switches.
- 2026-10-06 (per-vertex local lights, default chosen, owner to confirm): instance sets stay **per pixel** unless a set or its material says (`INSTANCES_LOCAL_LIGHTS_DEFAULT`), against the plan's per-vertex default: measured on the Iris Xe at 1080p, per vertex was not cheaper for the default set — village class 2.718 vs 2.705 ms scene pass (on vs off), with 12 lamps over its scatter 6.88 vs 6.78 ms, Skyforge 3.441 vs 3.419 ms (its view holds no point lights), +2 shader modules and +1 pipeline. - 2026-10-06 (per-vertex local lights, implementation): per-vertex light is diffuse only (N·L × colour × falloff, no highlights or shadows, as Unity), added to the ambient irradiance (every lighting model takes it, before the probes replace the held ambient). Double-sided surfaces take |N·L| (a vertex can't tell the face). The sum is built in the vertex stage's own flow (a `setupPosition` hook on node materials, after instancing/skinning) because the effect pool loops over its slots in use and a varying's value can't hold statements; the fragment side reads it only when the vertex side summed. Vertex-stage values are uniforms of their own per light (a per-pixel light node's colour is swapped for a shadowed one by whichever build set up its shadow last). Which program an object gets can't depend on the object in three's keys, so a mode other than per pixel draws a *variant* of the material (`Object.create(material)`: reads every current value through the prototype, own program key = the material's values + the mode, dropped with the material) swapped in `renderer.renderObject` (precompile included); `mesh.material` never changes. Importances are part of the lights node's cache key (a change rebuilds lit programs once). Batches and merged cells key on the mode.

- 2026-10-06 (effect lights on the GPU, implementation): the light system is simulated on the CPU beside the GPU systems, not read back from the GPU and not driven by parameters. Measured: a GPU system costs 0.045–0.08 ms of main-thread dispatch a frame whatever its size (three's compute calls, gather, sort), the CPU step 0.01 ms + ~0.17 µs a particle; a light system holds a handful of particles, so the CPU step costs microseconds, where a read-back costs a buffer map a frame, shows the light a frame late, needs a GPU pass to pick the oldest living particles, and does not exist on WebGL 2. Driving the light from parameters would lose the particles' positions and colours the Lights block promises. The CPU systems run in the GPU executor's planner (`EffectInstance` `simulate`), so time, origin, parameters and random streams are shared and the light system moves exactly as on the CPU executor (unit-tested bit for bit). Events between systems still move a whole effect to the CPU (they need the source system's particles there).
- 2026-10-06 (effect lights on the GPU, default chosen, owner to confirm): in an effect that simulates systems on the CPU anyway, systems under 512 particles (`GPU_MIN_PARTICLES`) join them — Skyforge's fires (flames 64, smoke 48) went to the GPU without this and cost +0.5 ms main thread; the crossover measured is ~400 particles. Effects with no CPU system keep every system on the GPU as before, though small ones would be cheaper on the CPU too (owner to decide whether the rule applies to every effect: it would move Sprout's small effects off the GPU). Each new play of an effect with GPU systems builds its compute passes (~8 ms on its first frame, 3 compute pipelines a system; plays are pooled) — as before for GPU effects, now also for effects with lights whose other systems are large. The Lights block's mask is a number field (`lightMask`, 0–255, default 255 = every layer; the graph editor has no mask widget) and its `importance` is auto/pixel/vertex (default auto), like a scene point light; no schema bump (block fields with defaults). Pool slots are ordered forced-per-pixel, auto, forced-per-vertex, so each build shades contiguous ranges; per-object layer tests and the extra loops are built only when a game's effects ask (`EffectLights.abilities`, part of the lights' program key).
- 2026-10-06 (ambient occlusion, default chosen, owner to confirm): AO stays the look's effect (Post → Ambient occlusion, its radius and intensity, at the high quality level as before); the new project setting `ambient_occlusion` picks the kind: SSAO (default: half resolution, three's SSAONode with its depth-aware blur, 16 samples, strength ×3 so it darkens a crease about as GTAO does) or GTAO (quality, about 1.5× the GPU time) or off. - 2026-10-06 (ambient occlusion, implementation): three r186's AO nodes run after the scene pass, so the occlusion must come from somewhere before it. Not a depth/normals prepass (every object drawn twice: the CPU-bound games are short of draw calls) — the previous frame's occlusion, reprojected per pixel with last frame's matrices and kept where the depth matches (6 % + 5 cm; a just-uncovered surface gets none for a frame; moving objects' own creases lag a frame). It reaches the materials as a light (`ScreenSpaceOcclusion`, post-ao.ts) whose node multiplies the lighting context's `ambientOcclusion`, which three's lighting models (and the custom-lit model) apply to the indirect terms only. three's documented route, `builtinAOContext` on the scene pass, makes every material count as holding nodes: every object's uniforms rewritten each frame (187 vs 84 buffer writes a frame on the village class, +0.5 ms on WebGL 2) — rejected. The history is one render target the light owns, made as a render target before any program binds it, its size published as the light's shadow map size so three refreshes the bindings of node-free materials when it changes (the first two attempts read a destroyed texture on WebGPU: no occlusion).
- 2026-10-06 (render scale and dynamic resolution, default chosen, owner to confirm): render scale 0.5–1 (default 1), FSR 1 at the end of the stack (Unity URP's order: everything up to and including SMAA/FXAA runs at the scale, FSR 1 wants an anti-aliased display-space input), RCAS sharpness 0.2 (AMD's default); the Scene view always draws at full resolution. - 2026-10-07 (probe scaling, implementation): each tile is packed for the GPU once when its file is decoded (the decoded file is not kept; the packed bytes are held while the tile is resident, so CPU memory follows the budget, not the world) and uploaded with one region write (WebGPU `queue.writeTexture`, WebGL 2 `texSubImage3D` through three's copy) into a 3D texture allocated on the GPU only (`dataReady = false`); tiles take runs of rows in columns as wide as the widest followed tile, first fit, and growing copies the old texture on the GPU. The tile table and the index are fixed textures written in place and uploaded at once, doubled when too small. Index: a grid over the resident tiles' boxes grown by their fade, cells half the smallest tile per axis (≤ 2 tiles a side on a lattice, ≤ 65,536 cells, longer lists over sparse spreads, no tile left out), each cell listing its tiles in table order; the per-object pick goes through it too (CPU O(1) an object). Every tile in memory is decoded with `DecompressionStream` (native inflate; the general PNG decoder stays for other files). WebGL 2: three's material observer re-uploads an unchanged object's per-object uniforms and texture bindings only when a light's data changes (`needsRefresh` SHARED), so the probe light counts the store's revisions as its shadow map size (the AO light's device) and every lit object rebinds once per change; three's WebGL backend also rebinds a texture node's new texture only when the new one's version differs, so every probe texture gets a fresh version.
