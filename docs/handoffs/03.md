**Cause:** the scan as written (export.md §5.4: pattern d "exactly one
`fetch(` total", zero hits everywhere else) failed on the first
preview/export build, because pinned `three@0.186.0` ships inert
occurrences of four patterns; §5.3's "exactly one fetch" was bundle-wide
rather than engine-scoped; the esbuild option set was implicit (default
format is IIFE even for ESM entries); and dependencies.md §5 check 4
carried no exception for the packet-10 preview bundle.

**Changes (gate record items a–e):**
- export.md §5.3 — the exact esbuild 0.28.2 option set is now pinned for
  **all three bundles** (`bundle`, `platform: "browser"`,
  `format: "iife"`, `treeShaking: false`, `sourcemap: false`,
  `minify: false`; every other option at its 0.28.2 default, no extra
  flags/defines/aliases); the default-is-IIFE verification is stated;
  the single-fetch rule is restated as "exactly **one fetch initiated by
  engine code** (the bootstrap's relative `./snapshot.json`)"; the IIFE
  consequence (no top-level `await` in the bootstrap — §5.5 step 1 uses a
  `.then()` chain) is recorded.
- export.md §5.4 — pattern d restated engine-scoped; new **§5.4.1
  recorded-exception table** bound to `three@0.186.0` (npm tarball
  SHA-256 `61eeff9d7616005c9a481c796f52287d81fbbbc0d55eaca5565322924252c1aa`,
  registry integrity `sha512-cr/fIM2…HHkQ==`) with re-measured counts and
  a four-part binding (identity, flags, reference build, real-bundle
  exact counts); §4's `scanHits` re-defined as hits *outside* the
  exception scope; §7/§9 now reference the pinned option set + three
  identity.
- dependencies.md §5 check 4 — the §5.4.1 table now applies to the
  **packet 10 preview and the packet 12 export** bundles alike.
- the risk note above is extended from pattern h / packet 12 to patterns
  d/f/h/j and to packet 10 (item e).

**Re-measurement (2026-09-17, throwaway /tmp install of the exact pins —
