## Outcome

Editor Play now runs the actual game host from immutable artifacts for v3
projects. One captured input + one production composition for both hosts: the
backend builds the v3 play artifact set with the SAME shared M3 closure builder
the export uses (`buildContentClosureM3`, packet 58), and the preview wraps the
SAME single shared production host (`createGameHost`) — no second bootstrap,
controller or run-state owner (delivery.md §3.2 normative).

The accepted content/snapshot split (sessions.md §13.2/§17.6; the M2 wrapper's
header) is preserved exactly: **the v3 snapshot (scene) arrives only through
the nonce-verified `tl.snapshot` bridge** (the accepted §17.2.1 locator route
set has no scene route — a locator `scene.json` read is `path_rejected`), and
**the content arrives only through the locator** (the manifest v2 `buildId` +
the declared asset bytes). The manifest's `sceneDigest` is the identity the
preview verifies the bridge snapshot against.

**`packages/backend/src/play-m3.ts`** (new): `buildPlayContentM3` — the v3
counterpart of the M2 `buildPlayContent`: a thin consumer of
`buildContentClosureM3` that assembles the immutable v3 play artifact set:
`manifest.json` (the v2 document, opaque bytes to the version-agnostic
`PlayContentStore`, carrying `sceneDigest`), the declared kind-tagged assets at
their digest paths, and the prebuilt M3 bundle as the entry. NO `scene.json`
(the scene rides the bridge). Fails closed on the closure's closed set
(`blob_missing`, `asset_digest_mismatch`, `export_build_unavailable`/
`behaviors_unsupported` — CC-55-3, over-cap bundle).
**`packages/backend/src/backend.ts`**: the `startPlay` v3 branch — a v3 project
reads the captured state through the `readCapturedV3` seam (a revision drift
before the build is `play_build_unavailable`/`revision_conflict`), reads the
**M3** bundle (`readGameBundle('preview-m3.js')`) and builds via
`buildPlayContentM3`; the v1/v2 M2 path is unchanged (each branch reads its own
bundle — a v3 play does not require the M2 `preview.js`).

**`packages/editor/src/preview/preview-m3.ts`** (new, a SEPARATE entry):
`startM3Preview` — on the bridge-delivered snapshot, fetch the locator
`manifest.json` (v2 type gate + WebCrypto `buildId` self-identity + the
handshake's expected build), verify the snapshot scene re-hashes to
`manifest.sceneDigest`, then compose `createGameHost` with the manifest's
resolved `settings`/`game`, the Rapier port (`solver.gravityY =
settings.gravity_y`, one object — C35-5), the scene adapter, the input + audio
owners. `bootstrapPreviewM3()` is the v3 page entry (the locator's `game.js`):
bridge handshake (records the expected build) → nonce-verified `tl.snapshot` →
compose → mount → truthful `ready` (the title screen loaded, NOT gameplay
started). **The M2 `preview-bootstrap.ts` is untouched** (the wrapper is a
separate entry, never inlined into the M2 bundle — the binding M2 §5.4.1
bundle-scan test re-passes unchanged). `tools/build.mjs` builds the third
browser bundle `preview-m3.ts` → `dist/preview/preview-m3.js` (served as the
v3 `game.js`); `tools/build.test.mjs` updated (3 built). `tools/check-boundaries.mjs`:
the `preview-m3.ts` row (the only editor file allowed to import `game-host`,
delivery.md §4.3 editor-UI rule).

## Limitations / disclosures (flag for Gate O)

- **Scene delivery (bounded interpretation, PR-2 flag):** the v3 scene is NOT
  a locator artifact — the accepted §17.2.1 route set (packet-48 protocol) has
  no scene route, so the scene arrives via the nonce-verified `tl.snapshot`
  bridge (the accepted M2 content/snapshot split), verified against
  `manifest.sceneDigest`. This matches the M2 design exactly; no protocol
  refinement was needed (no new wire type).
- **Relay wire types (bounded interpretation, PR-2 flag):** the §5 relay
  (`tl_game_control`/`tl_game_observe`) is routed through the accepted HTTP
  routes (`/play/:id/control|observe`) over the play session's selected browser,
  as delivery.md §5.2 prescribes — the accepted packet-48 bridge schema has NO
  game-control/game-observe message types (adding them would reopen the
  packet-48-owned protocol section). The v3 preview entry uses the accepted
  bridge surface (handshake/snapshot/ready/stop) for the preview↔shell channel;
  the §5 typed relay is the backend↔SDK path. No schema change was made.
- **CC-55-3 stays open**: a v3 play carrying source-bearing behaviors fails
  closed (`behaviors_unsupported`) — the sample (packet 61) uses built-in
  modules only.
- **GLB model rendering gap (carried from 58):** the shared three-adapter
  realizes boxes/lights/surfaces/camera only — a visible packet-61 player must
  use a box; the `demo-0003` v3 project is box-based (0 media assets) and
  exercises the v3 play path end-to-end.
- The v3 `game.js` entry is `dist/preview/preview-m3.js` (the third
  `tools/build.mjs` bundle); the M2 `preview.js` stays byte-stable.
  `CapturedV3Read.scene/content` are `unknown` (the backend casts `content` at
  the single call site — the closure validates strictly).
