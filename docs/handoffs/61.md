## What was built

- **Original self-generated content** (`samples/beacon-reach/assets/`): five PCM
  WAV cues (`cue-{start,jump,checkpoint,death,goal}.wav`, mono 48 kHz 16-bit,
  44-byte RIFF/WAVE header, ≤ 2000 ms) and two glTF 2.0 GLB models (`courier.glb`
  — Body+Arm rigid parts + Idle/Run/Airborne clips; `beacon.glb` — a pillar). A
  deterministic generator (`tools/generate-assets.mjs`, idempotent), per-asset
  `provenance.json` (SHA-256 `sourceDigest` + `sourceByteLength` + recipe), and an
  explicit reuse `LICENSE`. No downloaded third-party content, no external
  image/audio references, no fonts.
- **Captured authored project** (`captured/project.json`, 18 entities / 7 assets):
  a real v3 project authored through the SAME `@thirdlight/commands applyMutation`
  the browser and MCP use (in-process — the identical function the backend command
  route calls; the HTTP transport was not exercised, disclosed below). The baseline
  is the workspace's NEW v3 project (the single default camera the v3 validator
  requires); the recipe then authors the rest via commands — no direct
  active-envelope editing. The game config (title/objective/instructions/spawn/
  killY/cues) + the accepted gameplay settings are authored as content.
- **Reproducible command recipe** (`recipe/commands.json`, 26 commands): the exact
  `applyMutation` sequence. Replaying it over the same fresh v3 baseline yields the
  EXACT captured scene + content (identical `sceneDigest`/`contentDigest`).
- **Traversable step trace, REAL physics** (`tests/integration/m3-sample/
  step-trace.test.ts`, 3 tests): the captured layout composed over the real
  `platformer` + `runtime` + `physics-rapier` (pinned 0.20.0) + `platformer-game`
  modules at the ACCEPTED settings (no retuned controller constants). A fall in the
  first pit before the checkpoint → death count 1, respawn at the START spawn (X≈3);
  the full traversal clears the low step, both hazards, both pits, activates the
  checkpoint once, and reaches the beacon (goal); a fall in the second pit after the
  checkpoint → respawn at the CHECKPOINT spawn (X≈24).
- **Sample integrity tests** (`tests/integration/m3-sample/sample.test.ts`, 4 tests):
  committed assets match provenance digests + the WAVs are the §41.4 PCM container;
  regeneration is idempotent; recipe replay reproduces the captured digests exactly;
  no hardcoded runtime IDs (every command-authored entity is auto-generated
  `<kind>-<NNNN>`, every content reference resolves).
- **Owner-run browser procedure** (`tests/browser/m3-sample/README.md`, S1–S10): the
  visual + audible half — **UNVERIFIED in-container** (no browser/GPU/audio,

## Limitations + disclosed interpretations

- **GLB rendering gap (carried, Gate O F5):** the three-adapter realizes
  boxes/lights/surfaces/camera only; the visible player is a BOX and the GLB
  courier/beacon are imported content (declared in the closure) not rendered as
  animated models. The step trace + integrity tests are unaffected (they use the
  physics/logic runtime, not the render adapter).
- **In-process capture:** the sample was authored via in-process `applyMutation`
  (the identical function the backend command route + MCP call), not the HTTP
  transport. The command path is byte-identical; the HTTP/MCP transport is not
  exercised for the capture. Disclosed.
- **Independent decoration prefab copies (surface item not fully met):** the sample
  imports the GLBs as direct model entities (model-0001/2/3), not as independent
  copies of a decoration prefab. Given the GLB rendering gap, prefab copies would be
  non-rendering content. Disclosed — Gate P may accept or require a scoped
  box-based decoration-prefab repair.
- **Browser/visual/audible rows UNVERIFIED** (no browser/GPU/audio device
  in-container, packet-38 baseline §1).
