# Handoff 12 — Standalone export

## Outcome

Complete. A new `@thirdlight/exporter` package (`packages/exporter/`) implements
`exportProject(ctx)` (export.md §4) — the M1 standalone export — plus the
backend's admin route `POST /api/v1/admin/projects/:projectId/export`
(sessions.md §6.3; admin scope; never a browser command, not an MCP tool in M1).

The exporter produces a static browser tree from an **immutable valid M1 scene
snapshot using the SAME runtime used by play mode** (export.md §5.1: the bundle
is built from `packages/exporter/src/export-bootstrap.ts` → `runtime` +
`three-adapter` + `three`, the same sources/pins as the play-preview bundle —
no separate gameplay implementation). Output layout (export.md §3, normative):

```
<exportRoot>/<projectId>@r<revision>/
  index.html      minimal page: <canvas id="game"> + <script src="./js/main.js" type="module"> + HUD line
  js/main.js      the esbuild browser bundle (§5.3 pinned options, IIFE)
  snapshot.json   the runtime snapshot document (canonical: fixed key order, 2-space, LF, one trailing \n, no BOM)
  meta.json       the §6 metadata document (exact fields, recorded dependency versions)
```

**Design — pure-Node exporter, injected dependencies.** The exporter's own
source imports no Node builtins (dependencies.md §4.1: `node: []`): the
workspace service is injected (types-only edge — the backend passes its
instance; the exporter never touches the authoring files, never opens a second
authority) and ALL filesystem/path I/O goes through an injected `ExportFs`
facade supplied by the backend (which is allowed `node:fs`/`node:path`).
`esbuild` (its only external runtime dep, §7) runs with `write: false` so the
built bytes stay in memory for the scan. The browser bundle entry
(`src/export-bootstrap.ts`) is NOT a public export (the `.` subpath is the
export operation only); its §4.2 bundle-graph edges (runtime/three-adapter/
project-model/three) are enforced by a documented entry-file override in
`tools/check-boundaries.mjs` (the transitive graph is enforced at export time
by the esbuild `--metafile` check — export.md §4 step 4).

**Validation pipeline (export.md §4, in order; any failure ⇒ structured error,
temp dir removed, previous tree untouched):**

| Step | Check | Code |
|---|---|---|
| 1 | project loads via the injected service (queryProject + paged queryEntities); the reconstructed scene re-validates (project-model `validateScene`); manifest cross-checks; the constructed snapshot re-validates against the runtime.md §2 boundary (strict wrapper shape, `snapshotId = <projectId>@r<revision>`, `scene.revision` match) and is **frozen** | `export_scene_invalid` (carries ≤ 10 error objects) |
| bundle build | esbuild 0.28.2, the §5.3 pinned option set (bundle/iife/browser/no-tree-shaking/no-sourcemap/no-minify), `--metafile`, in-memory | — (defects surface at 4/5) |
| 2 | the authoring revision is unchanged since the read (re-read through the service) | `export_snapshot_mismatch` (conflict; frozen vs current revision) |
| 3 | the target is under `<exportRoot>` and outside the engine repository tree and the authoring tree (realpath containment) | `export_output_path_invalid` |
| 4 | the bundle import graph (metafile `inputs`) is exactly the §5.2 allowed set — no backend/editor/workspace/commands/mcp-adapter/protocol, no other exporter file, no `node:` | `export_bundle_graph_forbidden` (offending modules ≤ 8) |
| 5 | the forbidden-content scan (§5.4 a–j) over every emitted byte, with the §5.4.1 recorded-exception table (binding: three identity = version + lockfile registry integrity; pinned flags; a reference full-core three build re-scans to exactly the table's counts; real-bundle exact counts) | `export_bundle_forbidden_content` (≤ 4 hits `{pattern, byteOffset, context ≤ 80}`) |
| 6 | writes to a fresh temp dir under `<exportRoot>` + atomic replacement (backup → rename → remove backup; a failure restores the previous tree) | `export_output_not_writable` |

Success result (export.md §4): `{ ok, outputDir, snapshotId, revision, files
(byte sizes, measured), scanHits: 0 }`.

**`meta.json`** (export.md §6, exact): `schemaVersion: 1`, `type:
"thirdlight-export"`, `engineVersion: "0.1.0"`, projectId/snapshotId/revision,
`exportedAt` (UTC second — the only time-varying field), `dependencies`
(three/typescript/esbuild — the REAL installed versions read from
`node_modules/*/package.json` — + `runtime: { fixedStepHz: 120, modules:
["thirdlight.demo:box-motion"] }` fixed per §5.1), `scene` summary
(entityCount/cameraId/boxCount).

## Serving the output (documented per the packet)

Serve `<exportRoot>/<projectId>@r<revision>/` with a **plain static HTTP
server** (`python3 -m http.server`, nginx static, …). **Opening `index.html`
via `file://` is NOT supported** (module loading, the relative `fetch`, and the
renderer context policy). No publishing to the internet (M1 non-goal, §8).

## Contract change requests (documented per AGENTS.md — no silent changes)

1. **sessions.md §13.7 (additive, optional):** the export route needs the
   engine installation root (the tree holding `packages/` + `node_modules/`)
   for step 3 containment and the §5.4.1 identity/reference paths. No config
   field exists for it. **Proposed diff:** an optional `engineRoot` backend
   config field (+ the `THIRDLIGHT_ENGINE_ROOT` env var in the executable
   entry). Implemented as such; without it the export route fails closed with
   a structured `unavailable` error. Backward-compatible (existing configs
   unchanged; other routes unaffected).
2. **export.md §5.4.1 (reference-build entry under the pinned esbuild):** the
   contract's literal reference entry `import * as THREE from 'three';`
   elides to a 15-byte empty IIFE under the pinned esbuild 0.28.2 (verified
   2026-09-18: unused namespace imports are dropped even with
   `treeShaking: false`), making binding 3 unsatisfiable (it would require the
   table's counts in an empty bundle). **Implemented interpretation:** the
   reference entry references the namespace —
   `import * as THREE from 'three'; console.log(THREE.REVISION);` — which
   materializes the full-core bundle (1,777,839 B, consistent with the
   contract's 1,777,857-B re-measurement note) and re-scans to EXACTLY the
   table's counts (fetch( 3, process. 3, http:// 3, https:// 23,
   XMLHttpRequest 3; file:///WebSocket/__dirname/`node:`/`/api/v1/`/`/mcp` 0).
   The table's counts are UNCHANGED and remain the binding record; this is how
   to materialize the described "reference full-core three bundle" under the
   pinned toolchain.

## Limitations / notes

- `meta.json` `dependencies` values are read from the installed
  `node_modules/*/package.json` (three/typescript) and the esbuild `version`
  export — the recorded-versions requirement (charter §9) with the real
  installed versions.
- The exporter's unit tests use an injected fake service + in-memory fs
  (the package's `node: []` edge); the real-fs + real-service + real-HTTP
  end-to-end lives in the backend package's `export.test.ts` (where `node:fs`
  is allowed) — the same split as the backend/mcp-adapter boundary pattern.
- One export at a time per backend process is not enforced (the admin route is
  synchronous per request; concurrent exports of the SAME target would race on
  the atomic replacement — the last one wins, the previous tree is always
  either the old or the new complete tree, never partial). M1: operator-driven,
  single operator.
- Entity NAMES are scanned like any output byte (a name containing `http://`
  would fail the scan — contract-correct: the scan is over every emitted byte).
- The `engineRoot`-derived paths assume the engine tree layout
  (`packages/exporter/src/export-bootstrap.ts`, `node_modules/three`,
  `node_modules/typescript`, `package-lock.json`) — the M1 single-repo
  deployment (decision 0001 §6).
