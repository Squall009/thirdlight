## 1. Group A1 — deep isolation + JSON-safe diagnostics (R10, R17) — 2026-09-18

**Scope.** Exactly R10 + R17 of `docs/reviews/2026-09-18-commits.md`
(work-order group A1). The amended `docs/contracts/workspace.md` (dabfcff)
is the authority; the new claim-file/evidence-failure machinery is a later
group's work and is NOT started here.

**Findings fixed.**

- **R10 (P1, mutable authoritative state behind public query/ack objects).**
  Chosen isolation: a **deep freeze at the public API boundary** (not deep
copies) — queries are the hot path (workspace.md §5.3 immediate in-memory
  reads); a copy would re-allocate up to 1024 entities per query, while a
  freeze touches each shared object once and later exports/acks/replays
  skip it (`Object.isFrozen`, idempotent). Every public return —
  `runCommand` (fresh ack, replayed ack, failures), `query` (entity/
  subtree/scene/manifest/history/workspace + error payloads), all five
  operator operations and the scan report (`lastScan` getter included) —
  is deep-frozen (`deepFreeze`, `src/isolate.ts`); freezing recurses through
  the shared references, so the published scene entities, manifest, retry-
  record results and history change data become unreachable-for-mutation
  the moment they are exported. `runCommand` remains the single mutator of
  authoritative state (the commands layer is pure — verified: new object
  graphs, stored inverse/forward values deep-cloned on re-application —
  so frozen published snapshots never break the next mutation). The replay
  path still spreads the record top level (contract: byte-identical except
  `duplicated`), but its nested containers are frozen, so a replayed ack
  can no longer write through to the persisted record. A strict-mode write
  attempt throws `TypeError`; a sloppy-mode one silently no-ops — either
  way the state is untouched.
- **R17 (P2, unserializable validation errors).** Replaced the raw
  `error.found = <caller value>` with a bounded, JSON-safe diagnostic
  conversion applied at ALL public-input validation sites in
  `packages/workspace/src/errors.ts` (`invalidRequest`, `fieldUnexpected`,
  `fieldTypeError`, `fieldValueType`). Limits chosen: depth 8; 64 total
  nodes (containers + leaves); strings (values AND keys) truncated at 200
  chars with a total-length marker; ≤ 64 keys per object (rest ⇒ summary
  key); identity seen-set for cycles ⇒ marker string; unsupported
  primitives/exotics (BigInt/Function/Symbol/undefined/Date/Map/Set/typed
  arrays/class instances) ⇒ their type name as a string; non-finite
  numbers ⇒ string form. Output is always JSON-serializable and ≤ ≈ 30 KB
  for any caller input. Error codes/paths/messages unchanged — only the
  `found` representation.

**Findings fixed.**

- **R11 (P1, non-canonicalizable fresh input poisons its own envelope).**
  New step 0 of `runCommandImpl` (`src/service.ts`): a canonicalizability
  gate BEFORE project resolution, deduplication and any record
  construction. `canonicalIssue(value)` walks the ENTIRE request value
  under the digest's canonical rules (commands.md §6.6 — the same
  canonical-bytes semantics the model's serialization relies on): plain
  objects/arrays, finite numbers, strings, booleans, null; rejects
  undefined/BigInt/Symbol/function, non-finite numbers, exotic objects
  (Date/Map/Set/typed arrays — the canonicalizer would silently fold an
  empty-keyed Date into `{}`, bytes that disagree with the JSON wire
  form), class instances, and cycles (stack-based; shared DAG references
  are still legal JSON and pass). On failure: structured
  `invalid_request` / cls `validation` with the offending JSON-pointer
  path and the A1 bounded `found` conversion; NOTHING is written (no
  session claim, no record, no digest). The `D!` suppression site is
  removed: `digest: D` with `D` proven non-null by step 0 plus a
  defensive null branch that fails closed with a structured error — a
  null digest can never reach a record. The gate covers the whole request
  (op/projectId/expectedRevision/requestId/args/origin), which is the
  strict reading of "digest of the fresh payload is non-null"; valid
  requests are unaffected (dedup/pause/revision ordering preserved —
  pinned by the R11e sanity test).
- **R12 (P1, malformed persisted JSON aborts service startup).**
  `src/envelope.ts`: every discriminator is validated as a PRIMITIVE
  before any coercion — `result.op`, `change.type`,
  `originOfApplied.kind` (the audit siblings of the review's lines 344
  and 432); redundant `String(...)` on already-`typeof`-guarded values
  (projectId/requestId/appliedOf) dropped. A JSON object such as
  `{"toString":0}` now yields the existing structured load-error path
  (`retry_records_invalid` ⇒ project blocked per §7.5) instead of
  `TypeError: Cannot convert object to primitive value` from `String()`.
  `validateEnvelope` is total on JSON-derived data (parse/scene/regex
  sites audited: `parseDocumentBytes`, `validateScene` and all model
  checks are total; all remaining `RegExp.test`/coercion sites are
  typeof-guarded), so the startup scan (`scanEntry`) and the on-demand
  open can no longer throw from one corrupt project; the scan reports it
  (`loadable: false`, `code: retry_records_invalid`) and the healthy
  sibling is unaffected.
- **R13 (P2, historical retry payloads not strictly validated).**
  `src/envelope.ts`: retry records are strictly validated at load.
  (a) Enclosing-project consistency: `result.projectId` must EQUAL the
  envelope's projectId (create/mutation records); a mismatch rejects the
  record. (b)+(c) Complete entity/change payloads per the MODEL
  AUTHORITY: new `validateHistoricalEntities` runs `validateScene`
  (project-model §9/§10: known entity fields only, `components`
  present, component shapes validated, cross-entity reference/cycle/
  parent-before-child rules) over a SYNTHETIC scene — a synthetic camera

  transform-only placeholder parent per referenced-but-missing parent id

  entity and every `restoreSubtree` entity (previously only `id` was
  checked). Change ids/rootIds/deletedIds now must use the project-model
  ID syntax. Rejection ⇒ `retry_records_invalid` ⇒ the project is
  BLOCKED per §7.5 (commands and queries return `project_unavailable`

**Self-reclaim (§6.2 row, normative).** If the record is already exactly

write); missing/foreign ⇒ `ownership_conflict` (holder null), refuse to
serve. The EEXIST re-evaluation reaches the same row (a concurrent
re-open of our own record while we hold the claim file).

**Orphan-recovery rule (the ONLY liveness-referenced path).** Step 1
EEXISTed and the record supports the target epoch (absent/released/
older-epoch/unreadable): read claim-e's content — reclaim (rewrite
claim-e with our own step-2 identity + fsync, continue at step 4; steps
5–6 unchanged) ONLY if the content is parseable and the holder pid is
proven DEAD under the §6.2 liveness rules (unknown ⇒ live ⇒ refuse).

the holder content if parseable, and the liveness outcome). A live
holder's file is never removed or rewritten by any backend path;
concurrent claimers are serialized by O_EXCL alone. Reclaim rewrite uses
direct `node:fs` truncate-in-place (the WriteOps seam exposes no
truncate-open primitive; unlink+recreate would open an absence window a
third claimant could enter) — recorded interpretation; the claim-file
read/absence paths still go through `ops`.

unlinks `claim-e` best-effort AFTER its own record W is durable (a crash
in between leaves inert `released@e + claim-e` residue, reclaimed by the
next claim at e+1 or refused by orphan recovery if the holder is live);
a failed/unproven claim never unlinks a file that is not its own. The
safety argument (holder no longer an active writer; epoch is monotonic)
