## Outcome

**Implemented and complete, awaiting review.** The
`@thirdlight/commands` package (pure node-side layer; the only edge is
`@thirdlight/project-model@0.1.0` exact — dependencies.md §4.1) implements
the command contract (commands.md): pure mutation validation/application
and in-memory history semantics. No filesystem, transport, UI, three.js,
or Node builtins in package sources (check-boundaries: 0 violations).

- **Public API** (index.ts, per dependencies.md §3): `applyMutation(state,
  request)` (total — never throws; returns `ApplyOutcome`),
  `createCommandState(scene)`, `ERROR_CODES` (the 21 §5.4 codes),
  `MAX_REVISION` (2^53−1), and the wire types (request envelope,
  success/failure results, `CommandError`, change data, inverse specs,
  history model).
- **Pipeline** (apply.ts): strict envelope validation (`invalid_request`,
  JSON-Pointer paths) → revision check BEFORE argument validation
  (`revision_conflict`) → `revision_exhausted` → strict args schema
  (`field_missing`/`field_unexpected`/`field_type`/`field_value`, nothing
  silently dropped) → per-op preconditions (`entity_not_found`,
  `reference_missing`, `limits_exceeded` with limit/current/max) → pure
  application on a copy → project-model re-validation of the resulting
  scene (value constraints surface as `detailDocument: "result-scene"`
  details, capped at 32) → uniform `no_change` (canonical bytes, revision
  masked). Every failure leaves the input state byte- and history-unchanged.
- **Ops** (ops.ts): `createEntity` (smallest-free `<kind>-NNNN` per
  document, end-of-array append, defaults via the model), `setTransform`
  (whole-field replacement, full previous/next, canonical changedFields),
  `deleteEntity` (subtree closure, `deletedIds` in pre-deletion array
  order).
- **History** (history.ts): entries + cursor + per-session seq; fresh edits
  truncate the redo tail; `undo` applies the recorded inverse (delete /
  setTransform-restore / restoreSubtree with exact pre-deletion indices);
  `redo` re-applies the recorded change values (no re-scan); defensive
  `history_invalid` for inapplicable recorded inverses; `history_empty`
  with `which`. Success payloads carry the fixture-pinned key order;
  failures carry the §5.2 echo rules (op ≤ 32 chars, requestId ≤ 64).
- **Tests**: 8 suites, 144 tests. Scenarios 03/04/05 replay the packet-02
  fixture timelines verbatim (9-step undo/redo replay matches every
  fixture `out` and the disk-after bytes; all four scenario-04 rejections
  match with state byte-identical; stale-revision + re-issue recovery).

**Atomic batch behavior:** the prompt includes it "if and only if the
contract includes it" — commands.md defines exactly the five single

## Limitations / honest notes

- **Result-scene value constraints:** numeric/value rules (quaternion
  norm tolerance, §10 ranges, `-0`) are enforced by re-validating the
  resulting scene with the model — the single value authority — and
  reported as `result-scene` details; the command layer adds no second
  numeric authority.
- `box: {}` is accepted on `createEntity` (the model fills defaults);
  strictness applies to unknown fields and wrong types.
- `id_exhaustion` is unreachable through the public entry point from a
  valid M1 scene (the 1024-entity `limits_exceeded` fires first); the
  ID scan is unit-tested via the internal `nextEntityId` (create.test.ts).
- `duplicated` is always `false` in the pure layer — request
  canonicalization/dedup, durable revision, and the workspace-only
  codes (`project_not_found`, `request_id_reused`, `write_failed`, …)
  belong to the workspace package (packet 07). Query ops are likewise
  workspace-served (workspace.md).
- Undo of `setTransform` restores the full previous transform, so the
  undo change reports all three `changedFields` (pinned by scenario 05).
- Tests read fixtures via the Vite `import.meta.glob(..., { query: '?raw' })`
  pattern (same recorded approach as packet 05; boundary check exempts
  only vitest, and no new dependency is allowed by §7).
