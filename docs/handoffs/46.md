## Outcome

`ENVELOPE_STORAGE_VERSIONS` is `[1,2,3]`; `buildEnvelopeBytesV3` emits the
§16.3 canonical six-key envelope with the six-key content key order. The v3
load branch (§16.4) runs: envelope six-key set → **§16.2 combination check
before any field validation** → content six-key set + `validateContentV3`
(which enforces `content_bytes` ≤ 1 048 576 and `game_bytes` ≤ 16 384) and
`validateSceneV3` (both error sets reported) → retry block (v3 op set incl.
`applySurfacePreset`/`setGameConfig`). The session loader runs
`validateProjectV3` as the step-5 cross-block check. v3 envelopes are written
through the same `W`/§5.3 ack timing as v2 (one `envelopeBytesFor` used by the
mutation write, release rewrite, external-state resolution and the copy) — no
second mutation path, no side-car file.

`migrateProjectCopyV3` (§16.5): v2-pipeline-loadable source under the v2
registry, not live-owned, new valid ID, no destination/marker conflict; v1/v3
source refused `migration_version_unsupported`; a missing/tampered source blob
refused before any write. Destination: new identity, manifest stays 1, scene
2→3 verbatim, content verbatim except the four derived-revision resets to 0,
`game: null`, storage 3, revision 0, retry cleared/retention 128, empty
history. Four-phase marker (`created`→`manifest`→`blobs`→`envelope`,
`storageVersion: 3`, `sourceVersion: 2`, `newVersion: 3`),
destination-first/authoritative-last, idempotent/resumable, 120 s bound; the
exact reported object. `phase:"envelope"` + loadable envelope verifies and
removes the marker without rewriting; `phase:"created"` + an unexpected
non-marker file ⇒ `migration_destination_exists` unless a `W` temp (cleaned);
every refusal writes nothing and leaves both trees byte-identical. The v2
operator and its `storageVersion: 1` marker are preserved;
`readMigrationMarker` accepts both versions and the scan reports
`migration_resume_required` for either — including a marker-only destination
with no manifest (a bounded scan-order fix).

inherits the CC-44-6 precedence.
