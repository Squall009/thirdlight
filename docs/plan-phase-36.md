# Phase 36 — The block editor, kits and the trim sheet spec

Goal: going from a kit to a built level feels like one workflow. A **kit**
is one project item holding:
- a trim sheet;
- the style presets that use it;
- block types;
- pieces for doors, windows and the like.

The engine ships a **Basic Kit**, so a new level never draws grey. The
**block editor** is a full-screen edit mode in phase 34's shell. Its palette
comes from the kit, every block-type setting is editable in the UI (models
included), and rooms and buildings are a clearly named mode. Trim sheets
follow a **written art spec**, shared with the Texture Designer, and trims
are drawn at their real height instead of being stretched.

Read `plan-phase-34.md` and `plan-phase-35.md` first. The engine never
reads the game repos; nothing here is fitted to one game.

**Release checks run when the phase starts (36.0).**

## 1. Owner decisions (2026-10-12)

- **Kits as one item: yes.**
- **The block-kit workflow must explain itself.** The owner's questions
  were: must I supply meshes, or does Thirdlight have a basic geometry kit
  (ground, walls, stairs, buildings, interiors) that custom models such as
  doors and windows supplement? And what spec must a trim sheet follow to
  work with every kit?
- **Block layers blend four materials** like terrain. Built in phase 35;
  the block editor's paint uses it here.
- *Proposed, default chosen, owner to confirm:*
  - **"Kit swap" is renamed "Themes"** in the UI and manual. The data key
    `kits` on block types and layers stays, so no format change.
  - **A Kit references its parts.** It doesn't copy them: block types,
    presets and the trim material stay ordinary items and can belong to
    several kits.
  - **The Basic Kit is engine content.** It is read-only; **Derive** makes
    an editable copy, as starter presets work today. Its prototype trim
    sheet and placeholder door/window are game-ready assets with their
    triangle counts, LODs, collision, texture sizes and file sizes recorded
    in §5.
  - **Trim sheet defaults move to the Texture Designer's:** 2048², 512 px/m.
    The art-factory side is proposed to the owner separately (that repo
    isn't edited from here).

## 2. Where things stand (recon 2026-10-12, at `47999af5`; re-read at `6f191f50` after phase 35)

- **"Kit" means four things today:**
  - block-type "kits", a remap only (`block-kit.ts`);
  - "kit models", GLBs of named pieces (`three-adapter/src/pieces.ts`);
  - the `kit` shader (shown as "Atlas surface" since phase 35, `MATERIAL_SHADER_LABELS`);
  - in the manual, loosely, generated architecture.
- **The real built-in geometry is generated architecture**
  (`arch-generate.ts`, `arch-sweep.ts`, `arch-fill.ts`, `arch-roof.ts`,
  `arch-rooms.ts`):
  - walls, floors, ceilings, vaults, roofs, stairs, openings, frames,
    mouldings, buildings and interiors;
  - starter styles and presets in `arch-style-starters.ts` (room, tall
    room, hall, rail, fence, pipe), with `sheet: ''`;
  - with no trim material it draws flat grey (`architecture-view.ts:1266`).
- **Block types draw as coloured stand-ins** of their collision shape
  (`block-mesh.ts`). Under a trim material (or a layered surface with a
  trim layer) block faces wear strip UVs since 35.9 (`three-adapter/src/block-cell-uv.ts`):
  first storey `lower_wall`, higher storeys `upper_wall`, tops and
  undersides `floor`, one row per cell face, a row shorter than the cell
  stretched up the face. The starter template has no block types, kits or trim
  sheets, and it is 2D, so a 3D level needs hidden setup
  (`docs/manual/guides/block-layers.md:16-30`). The Inspector gives a block
  type a material (D258); Create → Material opens the **New material**
  dialog (Layered surface, Standard, Decal, Foliage, Water, Unlit, Atlas
  surface).
- **Giving a block type a model is MCP-only.** Looks, boxes, rotations and
  metadata are JSON fields the editor renders read-only
  (`session/descriptor-fields.ts:118-120`). Opening models
  (`opening.model`), segment overrides, repeat models, profiles and raw
  elements have no UI either.
- **Rooms** are the last of 20 tools in the block toolbar
  (`BlocksPanel.tsx:467`, 913 lines). There are two wall systems with no explanation:
  edge pieces painted on the layer, and walls generated by Rooms.
- **Trim sheets as implemented** (`project-model/src/trim-sheet.ts`):
  - defaults 1024², 256 px/m, 8 px padding, nine equal rows of 0.375 m;
  - every row tiles in u (4 m repeat);
  - since 35.3 the layered surface carries trim layers: `layerSheets` (a
    trim material per layer; the first sheet's rows feed the generator and
    the mip cap; sheets whose rows differ are a problem), so two sheets on
    one surface must share a row table — one spec layout makes that true;
  - a profile segment is stacked by `round(length / rowMetres)` and
    stretched to fit (`arch-sweep.ts:422-424`), so a 0.15 m baseboard on a
    0.375 m row is squashed 2.5×;
  - `layout.json` import maps layer names to slot ids literally;
  - the Texture Designer's sheet editor defaults to 2048², 512 px/m, 8 px
    gutters, 16 px alignment (its service's `normalize` still defaults
    alignment to 8); bands cost row + 2 gutters, so rows start 8 px into a
    16-aligned band;
  - there is no written spec (36.1 writes it).
- **Custom piece rules are undocumented:**
  - a piece node's own transform is kept (`pieces.ts:88-95`), so a piece
    away from the file origin draws offset;
  - there is no rule for UVing a segment-override model against the rows.

## 6. Decision log

- 2026-10-12 — Planned from the owner's questions about kits and trim
  sheets.

- 2026-10-13 (36.0) — Release checks and re-read. three.js 0.186.1 is the
  latest (no update); Rapier 0.21.0 is out, 0.20.0 stays pinned (a minor
  Rapier release is taken when something needs it; nothing in phase 36
  does). §2 brought up to phase 35's outcome. Defaults chosen, owner to
  confirm:
  - **Block faces stack field rows (added to 36.2).** 35.9 maps one row per
    cell face and stretches a shorter row up it; with the spec's rows that
    is `lower_wall` 2× on every first-storey block. Real height applies to
    block faces as it does to generated walls.
  - **The phase reduces e2e time (D253).** The two block files are
    rewritten anyway for the block editor; their target is −30 % (40.8 →
    ≤ 28 s of test time) and the block files together ≤ 52 s (from 64.2 s)
    with the block editor, kit editor and template steps inside them (§3).

- 2026-10-13 (36.1) — The trim sheet spec. Defaults chosen, owner to
  confirm:
  - **`lower_wall` is 0.5 m (256 px), not the planned 0.375 m.** A field row
    stacks a whole number of times; 0.375 m divides neither a 1 m nor a
    0.5 m block cell (2.67×), so block walls and 1 m-modular kits would
    stretch it. 0.5 m divides 1 m cells, 0.5 m half steps and 3 m storeys.
  - **The rest of the rows:** crown 0.125 m and frame 0.125 m (`tile_u`;
    the frame profile's default width is 0.12 m), column 0.25 m and bevel
    0.0625 m as **fields** (`tile_uv`: a shaft's face is stacked up the
    column and the wall top is 0.2 m wide, both wider than one row),
    emissive 0.125 m (`tile_u`), decals 0.25 m cells. Sum: 1,840 px of rows
    + 20 gutters = 2,000 of 2,048 rows. Kinds are a convention of the spec
    (the engine's row table only knows `tileV`); 36.2 reads `tileV` to tell
    a trim from a field.
  - **Rows start 8 px into 16-aligned bands**, as the Texture Designer's
    solver lays them (band = gutter + row + gutter, gutters not shared). The
    engine computes a safe mip level of 4 for this layout (the designer's
    `layout.json` reports `mip_levels_safe` 3, log2 of the gutter, which
    ignores the alignment).
  - **The spec says how things are today** where 36.2 changes them (fields
    stack with a stretch to whole repeats; trims follow the profile; block
    faces stretch one row): 36.2 and 36.8 update those lines.
  - **Diagram as ASCII** in the page, not an SVG: the manual has no images
    yet and `tl_docs` serves the pages as text to agents.
  - **Suggested piece budgets** (door or window 500–2,000 triangles at
    LOD0, ~½ LOD1, ~¼ LOD2) are guidance in the page, not an engine limit.
  - The art-factory changes (service default alignment 16, a Thirdlight
    starter sheet with the spec's rows, the albedo + height packing by
    default, the safe mip level) are a proposal for the owner, not edits.

- 2026-10-13 (36.2) — Trims at their real height. Defaults chosen, owner to
  confirm:
  - **Gated per sheet (`trim.realHeight`, additive on schema 7).** Absent:
    every part fitted to whole rows as before, block faces one row each —
    stored sheets keep their pixels. New sheets (Create, a shader switched to
    trim) and `layout.json` imports write it true (the designer paints rows at
    real height); the row table's **rows at their real height** box opts a
    stored sheet in. Sheetless (grey) architecture keeps the old equal-row
    layout, so its meshes are unchanged; the perf walls class pins the layout
    it was recorded with.
  - **Fields repeat at their own height, the last repeat cut** (it continues
    the one below: the row wraps in v), never stretched. A swept part counts
    from its lower end, so walls on one base line up and the cut lands under
    the ceiling, cove or dado rail; block walls count from the layer's row 0,
    as planar floors already do, so the pattern runs on across cells. The
    mesher cuts block wall faces at the repeat lines per block type ([first
    storey, higher storeys] metres from the type's real-height trim sheet,
    sent to the mesh workers with the types; a material redefinition re-cuts)
    with a vertex per repeat on each line; a mesh made before the cut keeps
    the fitted mapping. Faces no line crosses skip the cutting (its cost).
    Block tops map the floor row by metres too but are not cut (1 m cells and
    the 1 m floor row: as before).
  - **Trims are drawn once.** Within `TRIM_HEIGHT_TOLERANCE` (5 %) fitted:
    the starter room's 0.15 m baseboard on the spec's 0.156 m row and the
    starter frame's 0.12 m on 0.125 m both fit, so starters raise no problem.
    A shorter part shows the row's top at its painted scale; a taller one the
    row at the top and its bottom edge carried on (v clamped; the gutter
    repeats that edge). Curved runs (smooth profiles: a cove) stay fitted —
    a moulding's row is painted round its curve. Groin vaults follow the same
    rule; reveals keep their own mapping.
  - **Geometry never follows the sheet.** The simulation's colliders and an
    export's meshes are made without row tables, so a part keeps the
    slider's height; "its height comes from the row" is the slider's job: a
    Parameter wired straight into a band's height or a frame's width is tied
    to its slot's row (`arch-style-rows.ts`). The preset sliders show *Row
    “baseboard”: 0.156 m* and **Snap to row** (one graph edit); a tied value
    more than 5 % off its row on a real-height sheet is a warning in the trim
    material's backend problems (`materialProblems`, `tl_diagnostics`)
    naming the preset and both heights. Masked values are not judged.
  - **Meshing cost** (Node on this host, one 16² chunk): 3-high walls over a
    floor 2.4–2.8 → 2.6–3.0 ms (3,744 → 3,872 tris); worst case, every
    first-storey wall face exposed and cut once, 0.75 → 1.93 ms (1,536 →
    2,560 tris). The architecture test component: 1.1 → 1.0 ms, 3,002 →
    2,630 tris (trims no longer stack). Sheets without the flag: unchanged.
  - **E2E (D253):** `block-world-uv` carries the checks (block faces stack,
    a 0.4 m band keeps the 0.25 m baseboard row's scale, Snap to row in the
    Inspector) and got shorter: 6.7 + 6.7 → 6.4 + 6.3 s alone (its bump
    reads settle at 250 ms polls instead of 400).

- 2026-10-13 (36.3) — Kit data. Defaults chosen, owner to confirm:
  - **A kit is a resource kind** (`kit`, list `kits`, id `kitId`, one file
    each in `assets/kits/`), so the project window, index, search, moves and
    file watching handle it with no kit-specific code. The kind is marked
    **editor-only** in `RESOURCE_KIND_TABLE`: it may not get an address or
    labels (setLabels/setAddress refuse it), and the exporter's runtime
    content is an allow-list, so a build never carries kits. Pieces resolve
    to concrete references where they are used (an opening's `model`, a
    block look), so the runtime needs nothing from a kit.
  - **References are problems, never refusals**: a kit names its trim
    material, presets, block types and piece models; the model checks only
    shapes, and the backend logs a Problem per kit whose parts are missing
    or of the wrong kind (a non-trim material, a non-preset graph, a piece
    that is not a model, a thumbnail that is not a texture). Deleting a part
    a kit lists is never refused — the owner's "a kit references its parts".
  - **Shape:** `{kitId, name, description?, thumbnail?, trimMaterial?,
    presets?, blockTypes?, pieces?: {slot: [{assetId, piece?, weight?}]}}`.
    Standard slots (`KIT_STANDARD_SLOTS`): door, window, wall-override,
    corner, stairs, railing, roof-edge; any id-syntax name adds a custom
    slot. A slot holds 1–8 weighted pieces, the block look bound
    (`BLOCK_LIMITS.variants`), weights as block looks'. The data key is
    `pieces` (not `slots`) so it doesn't read like the trim sheet's row
    slots.
  - **`kitId`, not `kit`, on `blockLayer` and `architecture`**: beside the
    layer's existing `kits` (themes) a field `kit` would read as one of
    them. Shape-checked only (a dangling id is harmless and absent = none);
    it stays in exported scenes (a few bytes, ignored by the runtime) rather
    than adding a strip pass to the exporter.
  - **Until the kit editor (36.5)** a kit opens in the Inspector: its name,
    file, Delete, and a read-only list of its trim sheet, presets, block
    types and slots (standard slots always listed). Double-clicking any item
    kind without an editor now shows it in the Inspector instead of doing
    nothing.
  - **Themes:** visible labels (block panel, the block type's and layer's
    Inspector fields, tool docs, the manual's Blocks page) say Theme; data
    keys (`kits`), the script calls (`ctx.grid.setKit`/`kit`) and the perf
    tool's `--kit-swap` stay, as games call them. The MCP docs say "themes in
    the editor" next to the key.
  - The kit icon was generated with the Studio's container backend (Qwen
    Image Turbo, 8 steps; the GPU was in LLM mode), the established kinds
    prompt; `pack-editor-icons.mjs` takes an optional row name so one icon
    packs without the others' raw files.

  - The backend reads `kitProblems` through a new `@thirdlight/project-model/kits`
    value subpath (backend → project-model is types-only otherwise; the
    boundary check lists it with the other allowed subpaths). The regenerated
    reference split the content pages differently (assets and prefabs now on
    `content-blocks-scenes.md`); four manual links were moved with it.
