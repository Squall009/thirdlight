# Handoff 11 — MCP adapter for the external harness

## Outcome

Complete. `@thirdlight/mcp-adapter` (`packages/mcp-adapter/`) exposes the six
charter §7 capability categories (seven tools) over the **real MCP protocol**
using the pinned `@modelcontextprotocol/sdk@1.30.0`. Every tool routes into the
backend's `/api/v1` surface — the **same application services the browser uses**
— never a second mutation engine (decision 0001 §5). The server is a **stdio**
Node process (spawned by the harness, MCP over stdin/stdout). No general
eval/shell tool. No contract change was needed (the backend's session routes —
play start/stop, screenshot, diagnostics — were implemented in packet 09).

The package is **pure Node** (dependencies.md §4.1: `node: []`): no Node-builtin
imports in its own source — it uses global `fetch`, global Web Crypto
(`crypto`), and global `process`. It needs no `three` (decision 0001 §5), no
editor/UI, no browser. Node builtins the SDK's own types reference
(`node:stream`/`node:http`/`node:child_process` IOType) and the backend source's
(`node:http`/`node:fs`/`node:path`/`node:crypto`, `ws`) are declared in a local
ambient `src/ambient.d.ts` (type-only, mirroring the backend's own ambient
declarations; no `@types/node`, no Node runtime coupling).

**Transport decision — stdio, not streamable HTTP.** The harness (a coding
agent) launches a helper process and speaks MCP over stdio; the stdio server is
the canonical MCP delivery for a self-hosted, owner-launched server.
Streamable HTTP would require a listening HTTP server, which this package cannot
build (its boundary allows no `node:` builtins — no `node:http`). So the
deliverable is the stdio server (decision 0001 §5's "bash/CLI" analogue, using
the real MCP transport rather than a custom JSON protocol).

**No direct `zod` dependency.** The SDK's high-level `registerTool` requires
Zod schemas; instead this adapter uses the low-level `Server` with plain
**JSON Schema** `inputSchema`s and manual argument validation, so `zod` stays a
transitive (SDK) dependency only — keeping the §7 pin table exact (declaring it
directly would fail `check-deps`).

## Tools (→ backend route)

| Tool | Capability (charter §7) | Backend route |
|---|---|---|
| `tl_inspect` | bounded project/entity inspection | `POST /projects/:id/commands` (queryProject / queryEntity / queryEntities) |
| `tl_command` | command submission (bounded ops) | `POST /projects/:id/commands` (createEntity, setTransform, …) |
| `tl_sessions` | session listing | `GET /sessions` |
| `tl_play_start` | play start | `POST /projects/:id/play` |
| `tl_play_stop` | play stop | `POST /play/:psid/stop` |
| `tl_diagnostics` | bounded diagnostics | `POST /play/:psid/diagnostics` |
| `tl_screenshot` | screenshot from a connected browser | `POST /play/:psid/screenshot` |

`tl_inspect`/`tl_command` carry `origin: {kind:'mcp', clientId}` on the
mutation envelope (commands.md: the origin tag is an opaque audit label) and
inject `requestId` (via Web Crypto) when the model omits it. Responses include
the relevant `revision` / `playSessionId` / `snapshotId`; errors are the backend's
structured `code`/`fields` (e.g. `revision_conflict` carries `currentRevision`),
≤ 256 chars, with `isError: true`.

## Harness connection configuration (no real credentials)

The harness spawns the built stdio server and speaks MCP over its stdio:

```
# Command (the built, self-contained Node bundle — `npm run build` produces it):
node dist/mcp-adapter/mcp.mjs

# Environment (deployment values; injected per launch — never hardcoded/committed):
THIRDLIGHT_MCP_RUN=1                     # arm the executable entry
THIRDLIGHT_AUTHORING_ORIGIN=http://127.0.0.1:8501   # backend authoring origin (HTTP)
THIRDLIGHT_PROJECT_ID=<projectId>        # project to act on
THIRDLIGHT_MCP_TOKEN=<authoring token>   # owner-issued authoring:<projectId> token (secret)
THIRDLIGHT_MCP_CLIENT_ID=<clientId>      # audit tag for the origin field (default "mcp")
THIRDLIGHT_MCP_TIMEOUT_MS=<n>            # per-request timeout (default 15000)

# Transport: stdio — the harness writes MCP JSON-RPC to the process's stdin and
# reads responses from stdout. Logs go to stderr only (stdout is the MCP channel).
```

The token is a normal bearer credential for the backend's authoring scope; it is
passed in the spawn environment and sent as `Authorization: Bearer <token>` on
each backend call. No token is logged, and the MCP stdio channel carries no
token (only MCP messages). The harness's MCP client selection (e.g. which agent
connector consumes this server) is an owner deployment decision (decision 0001
§5 — pi has no built-in MCP client; pi-web does).

## Limitations / notes

- `tools/call` **over stdio with a live backend** is verified by composition
  (the stdio transport is proven by the spawn probe; `tools/call`→backend is
  proven by the in-memory e2e against the same `createMcpServer`/tools). A single
  in-package test cannot spawn the stdio child + a backend (the `node: []`
  boundary forbids `node:child_process`/`node:fs` in this package's source); the
  spawn probe was run outside the package as a one-off verification.
- `tl_command` accepts any op the backend's commands route accepts (bounded by
  the backend's envelope/op validation + the command services); the MCP layer
  validates argument shape, the backend enforces op semantics/revision.
- No embedded chat, no eval/shell tool (decision 0001 §5).
