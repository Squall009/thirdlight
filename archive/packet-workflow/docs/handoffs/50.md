## What was built

- **`packages/runtime` — the R1–R7 reset transaction.** `runResetTransaction`
  implements gameplay.md §5.1: R1 resolve the destination (the checkpoint
  `safeSpawnId` when active, else `spawnId`), R2 verify (inside level,
  `y ≥ killY`, no hazard overlap — pure reads), R3 clearance probe (the real
  Rapier `characterClearance` query), R4 physics reset (`clearCharacterMotion`
  + `placeCharacter` — the §5.2 restricted operations), R5 stage the pose, R6
  module `reset()` hooks (the controller zeroes velocity/coyote/jump-buffer/
  windows + the pending control intent), R7 apply + rebase (`prev := curr`, the
  player motion segment rebased to a zero-motion segment at the reset pose). A
  reset-phase failure fail-stops with no rollback (`failReset`: cancel driver,
  `stateName = 'failed'`, record the error, `session.markFailure` with the
  `reset:<label>` phase, publish the retained view). A test-only
  `injectResetFault` seam reproduces each R1–R8 signature (pinned by
  `fixtures/m3/gameplay/run/failure-phases.json`).
- **R7 motion-segment rebase (critical).** The stale pre-reset segment (the
  capsule falling in the pit, `y ≈ −8.2`) would sweep below `killY` in the
  respawn step's §4.2 swept-zone check, re-killing the capsule at the same step
  as the `respawned` boundary. R7 resets `lastSegments[player]` to a
  zero-motion segment and `playerMotion` to `{speed: 0, grounded: true}` — the
  no-render-streak guarantee (the display never sweeps between death and
  spawn).
- **`packages/physics-rapier`** gains `PhysicsResetPort` (`clearCharacterMotion`
  / `placeCharacter` / `characterClearance` → `blocked` / `no_support` /
  `query_failed`); **`packages/platformer`** gains the controller `reset(ctx)`
  hook; **`packages/platformer-game`** (verified sound, unchanged) keeps the
  swept §4.2 zone predicate.

`tests/m3-respawn/respawn.test.ts` (10/10) and `tests/m3-gameplay/course.test.ts`
(9/9), all over real Rapier:

- **Death before checkpoint** → real respawn at the start spawn (3, 0.91),
  grounded, no re-death at the boundary.
- **Death after checkpoint** → real respawn at the safe spawn (22, 0.91).
- **Nonzero velocity / windows / render-streak coherence** (the prev/curr
  rebase; the motion segment is zero at the reset pose).
- **Repeated deaths** (3×) → re-placed at the start spawn each time.
- **Buffered/held jump + pending control intent** → cleared by R6 (no leaked
  launch across the reset).
- **Blocked destination** (the real R3 probe) → `game_spawn_blocked`/`blocked`
  at step 13 (capsule at x=1 outside the wall; the start spawn x=3 inside it).
- **Stop during the delay** → the boundary runs when the driver resumes
  (step-based counter, not wall-clock).
- **Injected failure at each reset phase (R1–R8)** → the exact pinned
  signatures (code, reason, 1-based stepIndex, `reset:<label>` phase).
- **Failed runtime cannot resume** → `tick` returns `runtime_failed`; a run
  command on a failed runtime is rejected.
- **Snapshot unchanged** → the reset is a private world mutation; the authored
  scene is frozen.

## Key decisions / contract notes

- **The boundary event is published at the boundary, before R1–R7**
  (gameplay.md §3.2 item 0: "a boundary event is published at the boundary and
  is visible to every phase of the step that follows it"). The
  `check-fixtures.mjs` reference replay and the promoted `failure-phases.json`
  (`fail-reset-R1..R8` expect `runStarted` present) confirm this. A
  reset-phase failure therefore shows the boundary event present + `failed:
  true` + the session's `state: 'playing'` (T1/T5 set the state before R1). The
  view's `state` is the session's state; the runtime's fail-stop is the
  `failed` flag — matching the fixture's expected `state: "playing"`.
- **`tick()` returns `{ok: false, runtime_failed}` after a fail-stop** (a
  failed instance is never ticked again); the test harness `run.step()`
  tolerates this.
