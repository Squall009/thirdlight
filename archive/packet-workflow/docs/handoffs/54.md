- `src/audio.ts` — the injected owner of presentation.md §41.4.7 (the eight
  binding interface members exactly as contracted, closed `GameAudioError`
  codes `audio_decode_failed|audio_unsupported|audio_disposed|
  audio_invalid_bytes`, messages ≤ 256 chars log-safe):
  - **Rule 1 bytes-in**: `registerCue(assetId, Uint8Array)` — no URL,
    locator, `data:`, fetch, XHR, `<audio>` or base64 anywhere in the
    module; cue events carry `assetId` only.
  - **Rule 2 bounded async decode**: `decodeAudioData` on a **copy**
    (`bytes.slice()`); a failure (rejected promise OR a synchronous throw
    from a misbehaving platform) is a bounded per-cue diagnostic, never a
    throw across the host boundary; the supplied bytes are never mutated
    (both proven by test).
  - **Rule 3 voice cap**: `AUDIO_MAX_VOICES = 8` concurrent voices; a new
    cue at the cap is dropped with one bounded `voice_cap` diagnostic —
    never queued; every voice released on `ended`/stop (exactly once).
  - **Rule 4 dedupe**: each `GameCueEvent.id` plays at most once per owner;
    the current `runId`'s ids are kept and a runId change clears them
    (checkpointActivated never refires on re-entry — 40 §4.5).
  - **Rule 5 stale async work**: a runId change (stop/replay) and
    `dispose()` bump the epoch and stop every voice; a decode resolving
    after a run change is **discarded, never played** — and a fresh decode
    of the same asset is re-armed for the current run (the cue is an asset
    reference; run identity lives on the event, which `submit` re-checks —
    a stale-run event inside a current-run submit is skipped, never
    played). See "Interpretations" below.
  - **Rule 6 suspend on hidden/stop**: `setHidden(true)` suspends the owned
    context (voices keep their position — resume continues in place, no
    fast-forward, no replay); `setHidden(false)` attempts `resume()` only
    when already unlocked; a rejected resume **degrades to `blocked`, not
    an error**, and a later local gesture retries.
  - **Rule 7 local gesture unlock only**: `unlock()` is the host's real
    gesture call (the browser wiring checks `event.isTrusted` — this host
    and packet 55/62); the owner never unlocks on register/submit; the
    context is created at the gesture, never at load; `submit`/`registerCue`
    always succeed while sound-off (the game never waits for audio).
  - **Rule 8 close on dispose**: closes exactly the contexts it created,
    once; the second call returns `alreadyDisposed: true`; closing is
    synchronous w.r.t. public state (after dispose, every other method
    returns `audio_disposed`/`disposed`).
  - **Rule 9**: no Node builtins, no DOM in the owner (the module is
    deterministic with the injected `contextFactory` — it reads no clock,
    no timer, no global audio state); the browser entry's guarded
    `browserContextFactory()` (the only `window` touchpoint in the package)
    returns `null` when the environment has no Web Audio → status
    `unsupported`/`no_audio_context`.
- Status ladder (§41.4.6): `unsupported` (no factory / factory yields
  null) / `blocked` (pre-gesture autoplay, a rejected resume, or a
  created-but-closed context ⇒ `no_device`) / `ready` (`muted`,
  `unlocked` — a hidden-suspended context is a normal paused `ready`) /
  `disposed`.

## Limitations / interpretations

- **Stale decode re-arm (rule 5)**: the discarded buffer is never played
  (the contract's binding clause); a fresh decode of the same asset is
  re-armed for the current run so a legitimate new-run cue can still sound
  (the cue is an asset reference; the run identity is enforced on the
  event, which `submit` re-checks). Without the re-arm the first replay
  would permanently silence in-flight assets until re-registration —
  inconsistent with §41.5.3 ("the checkpoint cue sounds once per run").
- `registerCue` with a non-string `assetId` maps to the closed code
  `audio_invalid_bytes` (the set has no registration-shape code; the host
  always passes the typed `assetId`).
- Audibility UNVERIFIED (no device); the in-container browser (packet 38)
  has software WebAudio, so the browser procedure is runnable by the owner
  on that path if needed.
