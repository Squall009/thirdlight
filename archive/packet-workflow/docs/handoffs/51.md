## What was implemented

`packages/platformer-game/src/camera.ts` (new) — the `camera`-phase module,
`gameplay.md` §7 / runtime.md §12.1:

- **Pure `followCamera`** — the exact §7.2 pipeline: dead-zone overflow →
  smoothing (`k`; `k = 1` and the per-axis `CAMERA_MAX_STEP = 4` cap skipped on
  snap) → authored bounds → frustum clamp (centre fallback when the level is
  narrower than the frustum) → **no-write rule** below `CAMERA_SNAP_EPS = 1e-9`
  on both axes (no jitter). Bit-identical to the checker reference: the
  committed `follow.json`/`resize.json` fixtures replay bit-equal.
- **`createGameCameraModule`** — the single camera owner (§3.4/§7.6): writes
  `position.x/y` only in the `camera` phase (step) and the R6 reset barrier
  (snap, `reason`-driven: start/replay → start spawn, respawn → that spawn);
  authored Z/quaternion/scale never written; `transformOwners: [cameraId]`.
  Create-time defensive reads of `fovY`/`cameraFollow`/`game.level` (fail-stop
  on absent/invalid). A non-finite viewport (unreachable via `setViewport`)
  makes the step a no-write with one bounded `behaviorLog('warn',
  camera_viewport_invalid, …)` — never a fail-stop. The runtime's initial
  record `{width: 0, height: 0, aspect: DEFAULT_ASPECT}` (the "until
  setViewport" state, §7.1) is **not** invalid — the pipeline consumes the
  aspect, which the runtime keeps finite/positive.
- **`CAMERA_CONSTANTS`** + `CAMERA_Z`/`CAMERA_MAX_STEP`/`DEFAULT_ASPECT`/
  `CAMERA_SNAP_EPS` defined in-package. Boundary fix: the
  `platformer-game → runtime` edge is **types-only** (dependencies.md §4.1,
  enforced by `check-boundaries`); the runtime keeps its own export row
